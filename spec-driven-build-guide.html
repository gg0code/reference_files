Reference kit v2.8 · new project walkthrough

Spec-Driven Build Guide

Every step from an empty folder to a tagged release. Setup and the specification (Phases 0 to 3) are always done with you. After that, each requirement can be built along one of five paths, from most hands-on to fully unattended: guided (Claude writes code in chat, you check each step), assisted (the default: you approve the plan, loop.sh builds, the reviewer agent checks, you read the walkthrough and merge), autopilot level 1 (you approve plans, autopilot builds and opens PRs while you are away), level 2 (the reviewer agent also approves plans, you only merge) and level 3 (it also merges after green CI, you only release). Bugs always take the bug path. Compare the paths before Phase 4. Two agents do the work on every path: a builder (your Claude session plus loop.sh) and a read-only reviewer; the quality gate gate.sh decides when code is done. Fill in your project details and every command updates itself. Tick steps as you go; progress is kept per project name in this browser.

Start here · Choose your development path

Read once. You can switch paths between requirements at any time.

Phases 0 to 3 are the same for everyone: machine setup, the project, and the specification (idea, PRD, architecture, UI design, test plan, Issues). The specification is never automated: it is where you decide what gets built. The paths differ only in how each requirement is built after that.

Most hands-on

A · Guided

For: a tricky REQ, learning a new library, or when you want to see every line written.

Claude implements in the chat with the Implement prompt from the runbook, one step at a time. You run bash scripts/gate.sh yourself. Then review, explain and PR as in path B.

  • You approve: plan, every step, PR, merge
  • Speed: slowest · Cost: lowest
  • Guide: Phase 4, step "Implement" done by hand
Recommended · default

B · Assisted, one REQ at a time

For: your first project, and any REQ that touches money, security or data.

start.sh → next (plan) → you approve → loop.sh builds until the gate is green → review → explain → pr.sh → you review the PR → pr.sh merge.

  • You approve: plan, PR, merge
  • You read: the walkthrough, which teaches you the code
  • Guide: Phase 4
Semi-attended

C · Autopilot level 1

For: a batch of well-understood REQs after you have done 3 or 4 by hand.

You approve the plans first. bash scripts/autopilot.sh then runs branch, loop, commit, reviewer, fix rounds and PR for each, while you are away.

  • You approve: plans, then every PR and merge
  • Afterwards: type explain on each branch before merging
  • Guide: Phase 4b
Unattended build

D · Autopilot level 2

For: simple, low-risk REQs (screens, CRUD, reports) on a mature project.

AUTOPILOT=plan,build: autopilot also drafts the plans and the reviewer agent approves them (marked "by reviewer agent"). You only review and merge the PRs.

  • You approve: PRs and merges
  • Read those plans when you return
  • Guide: Phase 4b
Fully unattended

E · Autopilot level 3

For: experienced use only, with branch protection on and a strong test suite.

Adds AUTO_MERGE=1: waits for green CI, merges, runs the after-merge checks and continues. Stops on anything it cannot decide and lists it under "Needs you".

  • You approve: the release
  • Refuses to run without branch protection on main
  • Guide: Phase 4b
Any time

Bug path

For: anything that behaves wrongly, found by you, a user or a test.

start.sh bug "symptom" files the Issue and branch. Reproduce end to end, write a FAILING test, then fix with path A or B. A bug with no failing test is hidden, not fixed.

  • Never through autopilot
  • Guide: Phase 5

0 · Machine setup

Once per computer. Skip if done.

  1. Git identity and GitHub CLI

    Without a git identity the first commit fails, and the push later fails with src refspec main does not match any.

    git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
gh auth login
git config --global --list | grep -E 'user|default'

  2. Claude Code, jq, and your stack's tools

    Run the kit's scripts from WSL (WezTerm opens WSL inside tmux for you). jq turns on cost and token numbers in loop.sh.

    command -v claude      # Claude Code CLI must be on PATH
sudo apt install jq tmux
{TEST} --version 2>/dev/null || echo "install your {STACK} toolchain"

  3. Link the kit's dotfiles (optional)

    Makes the copies in the kit the live ones, so one edit updates both.

    ln -sf {KIT}/.bashrc     ~/.bashrc
ln -sf {KIT}/.tmux.conf  ~/.tmux.conf
cp {KIT}/.wezterm.lua /mnt/c/Users/gaura/.wezterm.lua   # WezTerm reads it from Windows
source ~/.bashrc && tmux source-file ~/.tmux.conf

  4. MCP prerequisites: Node.js and uv

    Every project gets three free MCP servers in .mcp.json: chrome-devtools and playwright (let Claude open and test your app in a browser) need Node.js 18+; graphify (a map of your codebase) needs uv. Details: docs/MCP.md in each project.

    node --version     # v18 or newer; else install the LTS from nodejs.org
curl -LsSf https://astral.sh/uv/install.sh | sh
uv tool install "graphifyy[mcp]" && graphify install   # adds the /graphify command to Claude

    If you skip this, Claude lists what is missing, with these commands, at the start of each session.

  5. Token savers: RTK and the cost status line (optional)

    RTK compresses command output before it reaches Claude (60 to 90 percent fewer tokens on git, grep and test output). The status line shows session cost and the active model under every prompt.

    curl -fsSL https://raw.githubusercontent.com/rtk-ai/rtk/refs/heads/master/install.sh | sh
mkdir -p ~/.claude && rtk init -g
grep -i rtk ~/.claude/settings.json    # hook registered?
    /statusline show session cost, today's total cost, and the active model

1 · Create the project

About two minutes. One command does the heavy lifting.

  1. Run the scaffold from the projects folder

    Creates the folder, git repo, CLAUDE.md, all docs (each marked Status: TEMPLATE), scripts/, CI for your stack, the first commit and a private GitHub repo. Run it from the folder that will hold the project, not inside it.

    cd {ROOT}
bash {KIT}/scaffold.sh {APP} {STACK}

    You should see: Result: SUCCESS, remote origin set, and CI .github/workflows/ci.yml. A WARN about gh means the local repo is fine but nothing was pushed; the output prints the exact fix.

  2. Sanity check

    cd {ROOT}/{APP}
git log --oneline     # at least 1 commit
git branch            # main
git remote -v         # origin
gh issue list         # runs clean (empty list is fine)

2 · Open the work session

Every time you sit down to work.

  1. Start a tmux session for this project

    WezTerm already runs tmux (session main), so create a separate session and switch to it instead of nesting.

    cd {ROOT}/{APP}
tmux new-session -d -s {APP} -c "$PWD" 2>/dev/null; tmux switch-client -t {APP}

  2. Make four panes and give each its role

    Prefix is Ctrl-a. Split with Ctrl-a | then Ctrl-a - twice. Right-click each pane and pick its role from the menu so the colours match the chips in this guide: Claude, Tests, Git, Development (frontend). Move between panes with Ctrl-h/j/k/l.

    • claude every prompt in this guide
    • test the watcher; you only look at it
    • git every shell, git, gh and script command
    • frontend dev server, wireframe, or the cost monitor

  3. Start Claude and run setup

    The first time in a new repo, accept the trust dialog (without it loop.sh runs untrusted and may not write files) and approve the project MCP servers.

    claude
    setup

    You should see: a table of every doc still at TEMPLATE or DRAFT, and the setup order. If an MCP server is not connected, also a short ✅/❌ list with the install commands (nothing about MCP when all are connected). Claude will not write application code until setup is approved.

  4. Check the kit is active (first session in a new project)

    Files and tools: one command reports PASS, WARN or FAIL for CLAUDE.md, every doc, the reviewer agent and its permissions, all scripts, CI, the tools, the MCP servers and their prerequisites, and how many docs are still templates. Fix every FAIL; TEMPLATE warnings are expected until Phase 3 is done.

    bash scripts/start.sh check

    Claude is reading them: ask this in the claude pane.

    Which project files have you read this session, and what does section 0 of CLAUDE.md tell you to do?

    You should see: CLAUDE.md, docs/RULES.md, docs/TASKS.md, docs/MEMORY.md, docs/MCP.md, the TEMPLATE/DRAFT setup check and the MCP check. Then type /mcp: chrome-devtools, playwright and graphify are listed (graphify connects once you have run /graphify .). If not, Claude was started outside the project folder: quit, cd {ROOT}/{APP}, start claude again.

    • Copied in by: scaffold.sh (Phase 1)
    • Loaded by: Claude Code reads CLAUDE.md automatically; CLAUDE.md tells it to read RULES, TASKS and MEMORY every session
    • Comments enforced by: scripts/doclint.sh, run by the loop, pr.sh merge, CI and the reviewer

3 · Specification

Once per project. Turns the idea into approved, traceable docs and Issues.
Rule for every doc: Claude drafts it with Status: DRAFT, you review it, you change line 1 to Status: APPROVED - {DATE}, then commit straight to main. Branches and PRs only start in Phase 4.

  1. Write the idea

    Fill docs/00-idea.md yourself, or dictate it to Claude. Rough is fine: problem, users, the idea in one sentence, what version 1 does, constraints. Then set line 1 to approved.

    git add docs/00-idea.md && git commit -m "docs: raw idea (approved)" && git push

  2. Interview, then PRD

    Interview me to produce docs/01-prd.md for {APP} from docs/00-idea.md.
Ask questions in small batches; do NOT write the PRD until I say "go".
When I say go, fill the template in docs/01-prd.md. EVERY requirement carries a stable
REQ-ID (REQ-001, REQ-002, ...), permanent and never renumbered, with testable acceptance
criteria. Functional and non-functional separated. No implementation detail, only what and why.
Leave line 1 as "Status: DRAFT".

  3. Review the PRD and cut scope

    The cheapest place in the whole project to say no. Keep version 1 to the Must requirements. Approve line 1, then commit.

    git add docs/01-prd.md && git commit -m "docs: PRD with REQ-IDs (approved)" && git push

  4. Architecture and UI design

    Fill docs/02-architecture.md from docs/01-prd.md.
Non-functional envelope: (users, data volume, response time, auth, deployment, offline needs).
Section 8 MUST be the traceability table: REQ-ID | component(s) | file(s) | notes.
Flag any REQ-ID with no row (gap) and any component with no REQ-ID (scope creep).
List every external dependency in section 6.
Then fill docs/03-ui-design.md: colour tokens for light and dark (WCAG AA), typography,
components, the empty/loading/error states, and section 9 listing every screen with its REQ-IDs.
Leave both Status lines as DRAFT.

  5. Review the traceability table both ways

    No REQ-ID without a row, no component without a REQ-ID, no external dependency you did not expect. Approve both, then commit.

    git add docs/02-architecture.md docs/03-ui-design.md
git commit -m "docs: architecture + UI design (approved)" && git push

  6. Clickable wireframe with REQ tags

    Build docs/03-wireframe/index.html: a navigable, clickable, single-file HTML wireframe
covering the full happy path for {APP}, following docs/03-ui-design.md.
Every screen or element that serves a requirement carries data-req="REQ-00X".
Add a "trace mode" toggle that shows a visible badge with each element's REQ-ID.
No backend; hardcode sample data.

    Open it in the frontend pane (explorer.exe docs/03-wireframe/index.html), click through, toggle trace mode.

    git add docs/03-wireframe/ && git commit -m "docs: wireframe with data-req tags (approved)" && git push

  7. Test plan, and fill in CLAUDE.md

    Fill docs/04-testplan.md: one row per test case TC-### | REQ-ID | type | steps | expected.
Every REQ-ID must have at least one test case; flag any with zero as UNVERIFIABLE.
Fill section 2 (regression gate) from the PRD's release acceptance criteria.
Then fill the FILL IN sections of CLAUDE.md (project, stack and commands, regression gate).
The full test command must include a doc-lint that fails on a missing directory README,
file header or function doc block. Leave Status lines as DRAFT.

    Review and approve, then commit.

    git add docs/04-testplan.md CLAUDE.md && git commit -m "docs: test plan + CLAUDE.md filled (approved)" && git push

  8. Tailor RULES and the launch checklist

    These two are mostly reusable, so Claude only proposes changes and you approve each one.

    Propose changes to docs/RULES.md (section 1 project rules) and docs/05-launch-checklist.md
for this project, as a numbered list of additions and removals with reasons.
Do not edit the files until I approve each item.
    git add docs/RULES.md docs/05-launch-checklist.md && git commit -m "docs: rules + launch checklist tailored (approved)" && git push

  9. One GitHub Issue per REQ-ID, then TASKS

    Read docs/01-prd.md. Create one GitHub Issue per REQ-ID, strictly one-to-one.
Do NOT group REQ-IDs unless two are inseparable (same code change, cannot be tested apart).
Title: "REQ-00X: short name". Body: the requirement + its TC-IDs from docs/04-testplan.md.
Label each "requirement". Use gh issue create.
Then fill docs/TASKS.md: phases in build order, each line "REQ-00X (#N) title" with the real
Issue number. Set its Status line to APPROVED.
    gh issue list
git add docs/TASKS.md && git commit -m "docs: TASKS with Issue numbers (approved)" && git push

  10. Close setup and protect main

    Approve docs/MEMORY.md with a first session-log line, then run setup once more. Once CI has run on GitHub at least once, turn on branch protection. From here on every change goes through a branch and a PR.

    setup

    You should see: nothing left at TEMPLATE or DRAFT.

    gh api -X PUT repos/{GHUSER}/{APP}/branches/main/protection \
  -F required_status_checks[strict]=true \
  -f "required_status_checks[contexts][]=test" \
  -F enforce_admins=false \
  -F required_pull_request_reviews=null \
  -F restrictions=null

4 · Build a requirement

Repeat for each REQ in TASKS.md. Nothing to type in: the scripts find the next REQ and its Issue.
Two human stops: the plan (step 3) and the PR (step 10). One agent gate: pr.sh will not open a PR until the reviewer says APPROVE. One hard signal: the test pane must be green. Lost at any point? bash scripts/start.sh status tells you where you are and what to do next.

  1. Start the next requirement

    Picks the first unticked REQ in docs/TASKS.md, finds its Issue number, and creates the branch (for example feat/REQ-003-profile). The branch name now carries the ID for every later step.

    bash scripts/start.sh

    You should see: Working on REQ-00X Issue #N title and the next action. It refuses if you are still on an unfinished REQ, so nothing gets lost.

  2. Plan only, no code

    Claude drafts docs/plans/<REQ>.md for the REQ in the current branch.

    next

  3. Approve the plan

    Read it. Fix it or ask Claude to revise. When happy, set line 1 to Status: APPROVED - {DATE}. loop.sh refuses a DRAFT plan.

    git add docs/plans && git commit -m "docs: approved plan"

  4. Implement: run the loop

    Fresh Claude context each pass, tests first, until the quality gate (bash scripts/gate.sh: docs, lint, complexity, format, types, full tests) is green or the plan's iteration cap is hit. Start the watcher in the test pane and leave it running.

    {WATCH}
    bash scripts/loop.sh

    You should see: LOOP COMPLETE - suite green, the touched files, and the exact commit line to use. Hitting the cap means the plan was wrong: read git diff and FAILURES.txt, re-plan, re-approve, re-run.

  5. Look at it

    If there is UI, run it and be picky: spacing, states, mobile width, dark mode. Missing docs, complex functions, missing type hints and format problems already turned the loop red, because the loop's exit condition is gate.sh. Check the UI against 03-ui-design.md. Small unrelated fixes (lint, typo, flaky test, obvious UI defect, under about 20 lines) go in their own chore(hygiene) commit. Anything bigger becomes a bug later.

  6. Commit locally

    Use the commit line the loop printed (it already contains the REQ and Issue), or:

    git diff
git add -A && git commit -m "feat: what this change does"

  7. Review by the second agent

    The reviewer runs on Opus in a fresh context, can only read, and checks the branch against the plan, the PRD row, the TC rows and RULES.md. Its report is saved to docs/reviews/<REQ>.md and committed.

    review

    You should see: Verdict: APPROVE or Verdict: CHANGES REQUESTED, with findings ranked Critical, Major, Minor.

  8. If CHANGES REQUESTED: loop again, then review again

    The loop reads the findings and fixes the Critical and Major ones, and lists any it disputes for you to decide. Skip this step when the verdict is APPROVE. Maximum 2 rounds; a second CHANGES REQUESTED means the plan is wrong.

    bash scripts/loop.sh
git add -A && git commit -m "fix: address review findings"
    review

  9. Read the walkthrough

    After APPROVE, Claude explains the change in plain language and appends it to docs/reviews/<ID>.md: what the user can now do, each file changed and why, the path a request takes (route, service, repository), and where to look if it breaks.

    explain

    Read it before the PR. If you cannot follow it, ask Claude to simplify the code now: this is the moment it is cheapest.

  10. Open the PR

    Pushes and opens the PR with the right title, Closes #N and a link to the review. Refuses until the review says APPROVE.

    bash scripts/pr.sh

  11. Review the PR, then merge

    Read the review report first, then the diff. You can overrule a finding, but write why in the PR.

    • Full suite green locally and in CI
    • Reviewer verdict APPROVE
    • File headers, function doc blocks and READMEs present
    • Architecture row and test plan still match the code

    Then merge. It asks you to confirm, waits for CI, merges, and runs the after-merge checks on main (full suite, CI status, traceability).

    bash scripts/pr.sh merge

  12. Finish the after-merge checks

    If pr.sh merge reported main red, revert first: it printed the commands. Otherwise:

    Audit traceability: for every REQ-ID in docs/01-prd.md, list its TC-IDs from
docs/04-testplan.md and whether each currently PASSES, plus its row in
docs/02-architecture.md section 8. Flag any REQ-ID with zero passing tests (UNVERIFIABLE),
any failing test, and any architecture row that no longer matches the code.
Output a markdown table.
    wrap up

    Then press Start next REQ above and go back to step 1.

4b · Autopilot (optional)

Instead of Phase 4, build several REQs unattended. Choose the level at the top.
Level 1 builds only plans you approved and stops at the PR. Level 2 lets the reviewer agent approve plans. Level 3 also merges after green CI. The spec docs always stay yours, and anything autopilot cannot decide lands under "Needs you" in its report.

  1. Dry run first

    Shows each REQ it would take from TASKS.md and what it would do. Changes nothing.

    {APCMD} DRY_RUN=1 bash scripts/autopilot.sh

  2. Start the run and walk away

    Caps keep it safe: at most 3 REQs, {COST} USD, 2 review rounds each, and it stops at the first REQ that needs you. Level 3 refuses to start without branch protection on main.

    git checkout main && git pull
{APCMD} MAX_COST={COST} MAX_REQS=3 NOTIFY_CMD="notify-send Autopilot" bash scripts/autopilot.sh

  3. When you are back: read the report

    ls -t .autopilot/*.md | head -1 | xargs cat
gh pr list
    • "Needs you": each line says what stopped and what to do next.
    • Plans marked by reviewer agent: read them, you did not approve them.
    • Open PRs: read docs/reviews/REQ-00X.md first, then the diff; merge with bash scripts/pr.sh merge on that branch, then Phase 4 step 11.
    wrap up

5 · Fix a bug

Repeat per bug. The BUG number is picked for you.
A bug with no failing test is hidden, not fixed. The failing test is committed on its own, before the fix.

  1. File the bug and start its branch

    Describe the symptom in your own words. The script takes the next free BUG number, files the GitHub Issue and creates fix/BUG-00X. Then add the steps, expected and actual result to that Issue.

    bash scripts/start.sh bug "login fails with an empty password"

  2. Reproduce end to end, write a failing test

    The bug in the current branch name: reproduce it end-to-end as a user would, using the steps in its
GitHub Issue, then write a FAILING test that captures exactly this bug. Do NOT fix anything yet;
show me the test go red.

    Check the test pane is RED, then commit the test alone:

    git add -A && git commit -m "test: failing test for the bug"

  3. Localise the cause

    The test is red. Give me the call-map: who calls the failing path, top-down, and your
single best hypothesis for the root cause. Don't patch yet.

  4. Minimal fix

    Apply the minimal fix for the bug in the current branch name. The failing test must go green and
the full suite must stay green. Do not weaken or skip any test.
    git add -A && git commit -m "fix: the cause in a few words"

  5. Review, PR, merge

    review

    Fix and review again until APPROVE (maximum 2 rounds), then:

    bash scripts/pr.sh
# review the PR on GitHub, then:
bash scripts/pr.sh merge

    Record the test in docs/04-testplan.md section 5.

6 · Release

When the Must requirements are merged and main is green.
The gate is docs/05-launch-checklist.md. Sections A (correctness) and B (security) block the release. An item with no evidence counts as Fail.

  1. Audit, without fixing

    audit

    You should see: every item marked Pass, Fail or N/A with evidence (tool output, file:line or screenshot), and a table of Fails with A and B first.

  2. Decide what to fix now

    Every A and B Fail must be fixed. Others can become Issues for the next version.

  3. Fix the chosen items

    git checkout main && git pull && git checkout -b chore/release-fixes
    fix A3, B1, D1

    Replace the IDs with yours. Each fix is re-checked with the same tool and shown before and after. Then commit, PR, merge, and run the after-merge checks.

  4. Release check and tag

    release check
    git checkout main && git pull
git tag v1.0.0 && git push --tags

Tips

Habits that keep the code easy to understand and the work cheap.

Understanding your code

Read every walkthrough

Type explain after each APPROVE and read it before the PR. It names the files, the path a request takes, and where to look if it breaks. Ten walkthroughs in, you know your codebase.

If you cannot follow the diff, do not merge

Ask in the claude pane: "Simplify this change so a returning developer can follow it. Keep behaviour and tests the same." Simplifying before merge costs minutes; after, it costs a bug.

Find where a change goes

Open the change map, docs/02-architecture.md section 3a. Rules are in service.py, storage in repository.py, pages and APIs in routes.py. Or search the REQ-ID: grep -rn REQ-004 src tests docs.

Ask "who calls this?" before changing it

With graphify connected, ask Claude for the callers and impact of a function. Without it, use your editor's Find References. Do not trust a Called by: line you did not just check.

Keeping requirements small

One REQ, one page of plan, about 300 lines of diff

If a plan does not fit on a page or the PR is much bigger, split the REQ in the PRD (new REQ-IDs, never renumber). Small PRs are the ones you can actually review.

Build the walking skeleton first

Before REQ-001: an empty app with config, logging, /health, a green gate, green CI and one real deploy. Deployment surprises cost minutes on day one and days at release.

Hitting the loop cap means the plan is wrong

Do not raise the cap and re-run. Read FAILURES.txt and git diff, then fix the plan with next, re-approve, and run again.

Two CHANGES REQUESTED rounds: stop

The plan or the requirement is unclear. Re-plan instead of a third fix round.

Quality gate

Fix style automatically, logic by hand

uv run ruff check --fix . && uv run ruff format . clears most lint and format errors. Complexity, type and test failures need a real fix.

Never loosen the gate to get green

No raised limits, GATE_SKIP, noqa or type: ignore without your approval and a written reason. The reviewer treats an unexplained one as Major.

Function too complex?

Ask Claude to split it into named steps or use early returns. A function you can read top to bottom without scrolling is the target.

Type errors are documentation

A strict-typing error usually means the code is unclear about what it receives or returns. Fix the type, do not silence it.

Cost, models and sessions

Right model for the job

Opus for PRD, architecture, plans and bug localisation; Sonnet for building; Haiku for commits, PR bodies and Issues. Switch with /model.

Fresh sessions are cheaper and smarter

Start a new claude session per REQ. State lives in git, Issues and docs, so nothing is lost. Use /compact when a long session slows down.

Keep MEMORY.md short

It is read every session. Under about 150 lines; wrap up archives old session log lines.

Autopilot: dry run, then caps

DRY_RUN=1 first, then keep MAX_REQS and MAX_COST low until you trust it. Read .autopilot/<run>.md "Needs you" first when you return.

Staying safe

Lost? Ask the script

bash scripts/start.sh status shows the current REQ, plan, review, PR and the exact next action.

Main is red after a merge

Revert first, diagnose second. pr.sh merge prints the revert command.

Secrets never in files

plan ... is not approvedChange line 1 of the plan to Status: APPROVED - {DATE} and commit.

you are on REQ-00X, which is not merged yetFinish that one first (start.sh status shows the next action), or FORCE=1 bash scripts/start.sh.
no reviewer APPROVE yet from pr.shType review in the claude pane; fix and review again if it asks for changes.
no Issue number for REQ-00XIts line in docs/TASKS.md must read - [ ] REQ-00X (#N) title.
looks ALREADY DONEIt is merged or its Issue is closed. Only after a revert: FORCE=1 bash scripts/loop.sh

pytest not found on PATHsource .venv/bin/activate, then re-run.

IDs

REQ-00XRequirement. Born in the PRD, permanent, never renumbered. One GitHub Issue each.
TC-###Test case. Always points at exactly one REQ-ID.
BUG-00XDefect. Gets its own Issue and a failing test before any fix.
#NGitHub Issue number. Not the REQ number; look it up every time.
