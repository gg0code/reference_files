Spec-Driven Build Guide

Every step from an empty folder to a tagged release. Setup and the specification (Phases 0 to 3) are always done with you. After that, each requirement can be built along one of five paths, from most hands-on to fully unattended: guided (Claude writes code in chat, you check each step), assisted (the default: you approve the plan, loop.sh builds, the reviewer agent checks, you read the walkthrough and merge), autopilot level 1 (you approve plans, autopilot builds and opens PRs while you are away), level 2 (the reviewer agent also approves plans, you only merge) and level 3 (it also merges after green CI, you only release). Bugs always take the bug path. Compare the paths before Phase 4. On every path you can follow progress, and approve, build and merge, from a live dashboard on your computer or phone. Two agents do the work on every path: a builder (your Claude session plus loop.sh) and a read-only reviewer; the quality gate gate.sh decides when code is done. Start with Your setup: choose Windows, Mac or Linux (on Windows also your shell: Ubuntu bash is recommended, Git Bash, PowerShell 7 and CMD are supported), check the folders, and press Save; every command is then rewritten for your shell and values, and only the steps for your computer are shown. Tick steps as you go; progress is kept per project name in this browser.

Start here · Choose your development path

Read once. You can switch paths between requirements at any time.

Phases 0 to 3 are the same for everyone: machine setup, the project, and the specification (idea, PRD, architecture, UI design, test plan, Issues). The specification is never automated: it is where you decide what gets built. The paths differ only in how each requirement is built after that.

Most hands-on

A · Guided

For: a tricky REQ, learning a new library, or when you want to see every line written.

Claude implements in the chat with the Implement prompt from the runbook, one step at a time. You run bash scripts/gate.sh yourself. Then review, explain and PR as in path B.

  • You approve: plan, every step, PR, merge
  • Speed: slowest · Cost: lowest
  • Guide: Phase 4, step "Implement" done by hand
Recommended · default

B · Assisted, one REQ at a time

For: your first project, and any REQ that touches money, security or data.

start.sh → next (plan) → you approve → loop.sh builds until the gate is green → review → explain → pr.sh → you review the PR → pr.sh merge. (next, review and explain are typed inside Claude; the .sh scripts in the git pane.)

  • You approve: plan, PR, merge
  • You read: the walkthrough, which teaches you the code
  • Guide: Phase 4
Semi-attended

C · Autopilot level 1

For: a batch of well-understood REQs after you have done 3 or 4 by hand.

You approve the plans first. bash scripts/autopilot.sh then runs branch, loop, commit, reviewer, fix rounds and PR for each, while you are away.

  • You approve: plans, then every PR and merge
  • Afterwards: type explain inside Claude on each branch before merging
  • Guide: Phase 4b
Unattended build

D · Autopilot level 2

For: simple, low-risk REQs (screens, CRUD, reports) on a mature project.

AUTOPILOT=plan,build: autopilot also drafts the plans and the reviewer agent approves them (marked "by reviewer agent"). You only review and merge the PRs.

  • You approve: PRs and merges
  • Read those plans when you return
  • Guide: Phase 4b
Fully unattended

E · Autopilot level 3

For: experienced use only, with branch protection on and a strong test suite.

Adds AUTO_MERGE=1: waits for green CI, merges, runs the after-merge checks and continues. Stops on anything it cannot decide and lists it under "Needs you".

  • You approve: the release
  • Refuses to run without branch protection on main
  • Guide: Phase 4b
Any time

Bug path

For: anything that behaves wrongly, found by you, a user or a test.

start.sh bug "symptom" files the Issue and branch. Reproduce end to end, write a FAILING test, then fix with path A or B. A bug with no failing test is hidden, not fixed.

  • Never through autopilot
  • Guide: Phase 5

  2. Install the tools with winget

    Open PowerShell (any version, no administrator needed) and install Git for Windows (it includes Git Bash: the kit's scripts and Claude Code on Windows both use it), the GitHub CLI, jq, Node.js, Python, uv, PowerShell 7 and Windows Terminal. winget skips anything already installed.

    winget install -e --id Git.Git
winget install -e --id GitHub.cli
winget install -e --id jqlang.jq
winget install -e --id OpenJS.NodeJS.LTS
winget install -e --id Python.Python.3.12
winget install -e --id astral-sh.uv
winget install -e --id Microsoft.PowerShell
winget install -e --id Microsoft.WindowsTerminal

    Close every terminal window and open a new one so the new commands are found. Then keep the kit's scripts with Linux line endings (otherwise Windows Git adds CR characters and every .sh file fails with $'\r': command not found), and check the tools:

    git config --global core.autocrlf input
git --version && gh --version && jq --version && node --version && uv --version && python --version

    You should see: six version numbers. If python --version opens the Microsoft Store instead, turn off the two python entries in Settings > Apps > Advanced app settings > App execution aliases, then open a new window.

  3. Let PowerShell run the kit's scripts (kitsh)

    The kit's scripts are bash. This adds a kitsh command to your PowerShell profile that runs them in Git Bash, in the current folder. Open PowerShell 7 and paste:

    if (!(Test-Path $PROFILE)) { New-Item -ItemType File -Force $PROFILE | Out-Null }
Add-Content $PROFILE @'

# spec-driven kit: run the kit's bash scripts through Git Bash, in the current folder
function kitsh { $env:CHERE_INVOKING = '1'; & "$env:ProgramFiles\Git\bin\bash.exe" @args }
'@
. $PROFILE
kitsh --version

    You should see: GNU bash, version 5.... If PowerShell says running scripts is disabled, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once and try again. From here on, kitsh scripts/x.sh runs a kit script and kitsh -c '...' runs a line of bash.

  4. Let CMD run the kit's scripts (kitsh)

    The kit's scripts are bash. This creates a small kitsh.cmd in your user folder that runs them in Git Bash, in the current folder, and puts it on your PATH. Paste it into PowerShell once (CMD cannot write this file cleanly):

    New-Item -ItemType Directory -Force "$HOME\bin" | Out-Null
Set-Content "$HOME\bin\kitsh.cmd" '@set CHERE_INVOKING=1& "%ProgramFiles%\Git\bin\bash.exe" %*' -Encoding ascii
$p = [Environment]::GetEnvironmentVariable('Path','User')
if ($p -notlike "*$HOME\bin*") { [Environment]::SetEnvironmentVariable('Path', "$p;$HOME\bin", 'User') }

    Open a new CMD window and check:

    kitsh --version

    You should see: GNU bash, version 5.... From here on, kitsh scripts/x.sh runs a kit script and kitsh -c "..." runs a line of bash.

1 · Create the project

About two minutes. One command does the heavy lifting.

  1. Run the scaffold from the projects folder

    Creates the folder, git repo, CLAUDE.md, all docs (each marked Status: TEMPLATE), scripts/, CI for your stack, the first commit and a private GitHub repo. Run it from the folder that will hold the project, not inside it.

    cd {ROOT}
bash {KIT}/scaffold.sh {APP} {STACK}

    You should see: Result: SUCCESS, remote origin set, and CI .github/workflows/ci.yml. A WARN about gh means the local repo is fine but nothing was pushed; the output prints the exact fix.

  2. Sanity check

    cd {ROOT}/{APP}
git log --oneline     # at least 1 commit
git branch            # main
git remote -v         # origin
gh issue list         # runs clean (empty list is fine)

  3. Run the starter app (Python stack)

    With the python stack, the project already contains a working, production-shaped app: settings checked at startup, /health, JSON logs with request IDs, friendly error pages, security headers, CSRF protection, a rate limit, database migrations, a Dockerfile, error tracking ready to switch on, and a UI kit (buttons, fields with inline errors, search, empty states, toasts with Undo, light and dark). A small Notes feature shows the pattern every feature follows. It passes the quality gate as delivered.

    uv sync
cp .env.example .env              # then open .env and set a long random SECRET_KEY and your APP_NAME
uv run alembic upgrade head       # creates the database tables
bash scripts/gate.sh              # all PASS
    uv run uvicorn app.main:app --app-dir src --reload

    You should see: open http://localhost:8000: the start page; Notes: try saving without a title (the message appears next to the field and your text stays), add a few notes, search, delete one and press Undo. That is the standard every screen of your app follows. Not on the python stack? Skip this step.

3 · Specification

Tips

Habits that keep the code easy to understand and the work cheap.

Understanding your code

Read every walkthrough

Type explain inside Claude after each APPROVE and read it before the PR. It names the files, the path a request takes, and where to look if it breaks. Ten walkthroughs in, you know your codebase.

If you cannot follow the diff, do not merge

Type inside Claude (claude pane): "Simplify this change so a returning developer can follow it. Keep behaviour and tests the same." Simplifying before merge costs minutes; after, it costs a bug.

Find where a change goes

Open the change map, docs/02-architecture.md section 3a. Rules are in service.py, storage in repository.py, pages and APIs in routes.py. Or search the REQ-ID: grep -rn REQ-004 src tests docs.

Ask "who calls this?" before changing it

With graphify connected, ask Claude for the callers and impact of a function. Without it, use your editor's Find References. Do not trust a Called by: line you did not just check.

Keeping requirements small

One REQ, one page of plan, about 300 lines of diff

If a plan does not fit on a page or the PR is much bigger, split the REQ in the PRD (new REQ-IDs, never renumber). Small PRs are the ones you can actually review.

Build the walking skeleton first

Before REQ-001: an empty app with config, logging, /health, a green gate, green CI and one real deploy. Deployment surprises cost minutes on day one and days at release.

Hitting the loop cap means the plan is wrong

Do not raise the cap and re-run. Read FAILURES.txt and git diff, then fix the plan with next, re-approve, and run again.

Two CHANGES REQUESTED rounds: stop

The plan or the requirement is unclear. Re-plan instead of a third fix round.

Quality gate

Fix style automatically, logic by hand

uv run ruff check --fix . && uv run ruff format . clears most lint and format errors. Complexity, type and test failures need a real fix.

Never loosen the gate to get green

No raised limits, GATE_SKIP, noqa or type: ignore without your approval and a written reason. The reviewer treats an unexplained one as Major.

Function too complex?

Ask Claude to split it into named steps or use early returns. A function you can read top to bottom without scrolling is the target.

Type errors are documentation

A strict-typing error usually means the code is unclear about what it receives or returns. Fix the type, do not silence it.

Cost, models and sessions

Right model for the job

Opus for PRD, architecture, plans and bug localisation; Sonnet for building; Haiku for commits, PR bodies and Issues. Switch inside Claude with /model opus, /model sonnet or /model haiku.

Fresh sessions are cheaper and smarter

Start a new claude session per REQ. State lives in git, Issues and docs, so nothing is lost. Type /compact inside Claude when a long session slows down.

Keep MEMORY.md short

It is read every session. Under about 150 lines; wrap up archives old session log lines.

Autopilot: dry run, then caps

DRY_RUN=1 first, then keep MAX_REQS and MAX_COST low until you trust it. Read .autopilot/<run>.md "Needs you" first when you return.

Dashboard and phone

Leave it open in the frontend pane

It refreshes every few seconds, so a glance tells you whether a build is on attempt 2 or waiting for you. Pausing the browser tab pauses the polling.

"Needs you" is the to-do list

It only lists what waits for a person. If it says "Nothing is waiting for you", the machines are busy or the work is done.

Read before you approve

"Read and approve" opens the plan first and asks you to tick that you read it. Approving a plan you did not read is how the wrong thing gets built.

Share progress safely

For a client or manager, use --read-only with Tailscale, or the "Summarise progress" text, which is written for non-technical readers.

Staying safe

"Blocked by the kit" is a hook doing its job

The project's hooks stop Claude from editing code on main, touching .env, force-pushing, hard resets, --no-verify and pushing straight to main. The message says what to do instead (usually bash scripts/start.sh for a branch). Never remove a hook to get past it.

The bell means Claude needs you

When Claude waits for a permission or an answer, the terminal beeps and the dashboard shows "Claude is waiting for you" at the top of Needs you.

Lost? Ask the script

bash scripts/start.sh status shows the current REQ, plan, review, PR and the exact next action.

Main is red after a merge

Revert first, diagnose second. pr.sh merge prints the revert command.

Secrets never in files

Keys go in .env (gitignored) and paid MCP servers use claude mcp add --scope local. CI runs gitleaks on every PR.

Something feels off with Claude

Ask: "Which project files have you read this session?". If CLAUDE.md, RULES, TASKS, MEMORY and MCP are not listed, quit and restart claude from the project folder.
